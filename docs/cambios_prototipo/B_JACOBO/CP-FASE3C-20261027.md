Se agregó únicamente al input presencial existente:

```typescript
idTipoTramiteTupa?: string;
```

Se reutilizan el nombre y el validador UUID de MPV, incluido el rechazo del UUID
nulo. Ruta original: POST /api/v1/tramites/ventanilla-presencial. Respuesta y demás
campos conservados. El frontend envía el UUID del registro seleccionado en el
catálogo; para NO_TUPA omite el campo, no envía un UUID artificial ni null.

Compatibilidad y omisiones:

- Una solicitud general antigua sin TUPA sigue el flujo anterior, sin crear una
  asociación supuesta a DocuCore ni un código de trámite inventado.
- El cliente actual valida la selección y siempre envía el UUID si selecciona TUPA.
- Un cliente antiguo que envíe el marcador formal `SUZ26-NNN — ...` en asunto sin
  UUID recibe 400 explícito antes de conectar para persistir. Debe actualizarse;
  aceptar ese caso silenciosamente perpetuaría el defecto.
- El marcador sólo detecta omisión/contradicción; nunca se usa para resolver el
  procedimiento. Si el código del marcador contradice el UUID, se rechaza antes
  del CUT. Una petición sin campo ni marcador se considera general: no es posible
  inferir una intención TUPA oculta en texto libre.

## 4. Relaciones canónicas comprobadas

En 127.0.0.1:5433/sigd_jacobo_demo, con rol técnico sigd_jacobo_user y
transaction_read_only=on, se verificaron:

- sigd_doc.tipo_tramite_tupa: PK tipo_tramite_id y código único.
- sigd_doc.expediente: PK expediente_id, CUT/codigo_expediente único y FK
  tipo_tramite_id al catálogo; solicitante_id referencia persona.
- sigd_tra.tramite: expediente_id único y FK a sigd_tra.expediente;
  codigo_tramite es la representación textual complementaria.

No existe una sincronización automática asumida entre esas referencias. El FK
de DocuCore es el vínculo canónico; el servicio obtiene y guarda el código en
TramiCore explícitamente. No se crea ninguna tabla de correspondencia.

El SELECT real de validación del servicio pasó con los 20 pares procedimiento–tipo
documental existentes y vigentes. Los permisos de columna INSERT/SELECT consultados
para los campos nuevos de persistencia ya existen; no se concedieron permisos.
Eso no demuestra una inserción exitosa ni valida todos los efectos de triggers.

## 5. Persistencia implementada en el servicio original

1. Valida identidad y tipo documental mediante las reglas existentes.
2. Valida el formato TUPA y consulta por UUID parametrizado, sin LIMIT 1 ni
   selección arbitraria. Exige una fila vigente y tipo documental asociado mediante
   requisito/tipo_documento_requisito. No altera obligatoriedad ni exige un archivo
   digital ficticio para una recepción física.
3. Rechaza ausencia, inactividad, incompatibilidad documental o contradicción antes
   del generador CUT y de las inserciones.
4. Conserva el generador canónico y la creación original de persona/expediente.
5. Para solicitudes TUPA crea sigd_doc.expediente usando exactamente el UUID que
   devolvió TramiCore, el TUPA validado, el mismo CUT y el mismo solicitante.
6. Inserta sigd_tra.tramite con ese UUID y el código leído del catálogo.
7. Comprueba las identidades y referencias devueltas por ambas inserciones; una
   respuesta incoherente produce TUPA_LINK_CONFLICT y rollback de la transacción propia.
8. Registra el asiento original y confirma sólo después de completar los vínculos.

No hay UPDATE de claves, ON CONFLICT que reasigne relaciones ni valores TUPA
por defecto. Un conflicto SQL se propaga al manejo existente y revierte la
transacción propia. Si se suministra un cliente transaccional externo, el servicio
usa esa misma conexión y deja COMMIT/ROLLBACK/liberación al llamador, como antes.

DocuCore conserva su estado predeterminado; TramiCore conserva RECEPCIONADO.
No se cambian FSM ni se presupone equivalencia de estados entre dominios.
No se crean adjuntos S3 ni documentos digitales para representar papeles físicos.

## 8. Pendientes y autorización necesaria

La vinculación está implementada y sus transacciones probadas con dobles. Falta
demostrar una inserción real y su recuperación en otra sesión. Para una futura
aceptación persistente debe autorizarse explícitamente una recepción identificada
en la demo: idealmente persona sintética ya existente, un TUPA vigente y tipo
documental asociado, un CUT, un expediente TramiCore, su fila DocuCore, un trámite
con código y un asiento, incluidos triggers propios. No se crearía un PDF ficticio.

La prueba preparatoria debe consultar primero si existe la operación ante una
respuesta incierta y no repetir automáticamente el POST. El asiento es inmutable;
no se debe prometer una limpieza por DELETE. Una recepción general no TUPA sigue
sin un FK TUPA, por diseño. No se hace backfill desde asuntos históricos.

La procedencia de requisitos 050/051/054 y su ratificación institucional siguen
pendientes de las fases anteriores; este cambio usa el catálogo actual sin
inventar ni modificar requisitos. No concede permisos RBAC ni nuevos privilegios SQL.
