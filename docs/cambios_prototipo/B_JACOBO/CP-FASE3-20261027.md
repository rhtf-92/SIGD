## 2. Correcciones nuevas

### Ciudadanía y ámbitos

El grant persistido CIUDADANO → EXPEDIENTE_LEER/GLOBAL sigue existiendo; no se
cambió ningún permiso en PostgreSQL. Según la restricción expresa de esta fase,
la lectura ciudadana debe depender de titularidad. Se excluyó exclusivamente la
contribución de ese rol a la lectura institucional en las consultas existentes de
facultades, alcance de Bandeja, Detalle y Storage. No se anula la titularidad ni
la facultad obtenida mediante otro rol institucional legítimo de la misma cuenta.
No es una nueva jerarquía ni un bypass privilegiado por nombre de rol: es una
restricción explícita del rol ciudadano solicitada para esta intervención.

Storage tenía además dos defectos comprobados:

- La consulta productiva falló en PostgreSQL con SQLSTATE 42703 porque seleccionaba
  area_origen_id/area_destino_id en asiento_registro. Se retiraron esas referencias.
- El acceso por área admitía áreas históricas del asiento. Ahora se usa el área
  actual de RutaDoc; sólo si no existe ese estado se aplica el área MP para los
  canales originales MESA_PRESENCIAL/MESA_VIRTUAL. No se amplió el ámbito.

### Clasificación documental y formulario

El clasificador exigía todos los tipos configurados, aunque requisito.obligatorio
fuera false. Ahora consulta bool_or(r.obligatorio) por tipo y sólo exige los tipos
marcados obligatorios. Con varios tipos posibles, un único archivo explícitamente
clasificado ya es inequívoco; sin clasificación sigue rechazándose. El tipo
principal pertenece siempre a un documento aportado: no se asigna FUT ausente.
Se mantienen el rechazo de duplicados, tipos ajenos, ID/código contradictorios y
condiciones documentales que el contrato no puede evaluar.

El paso 2 no permitía escoger la clasificación por archivo, aunque el estado,
DTO y envío ya soportaban tipoDocumentalCodigo/tipoDocumentalId. Se conectó ese
selector y sus validaciones dentro de StepDocumentos. Se comprueba pertenencia
al procedimiento, duplicados y requisitos obligatorios. No se alteró el DTO ni
StepConfirmacion: el envío existente ya transportaba esos campos.

## 5. Mesa de Partes y trazabilidad

- **Virtual:** conserva TUPA UUID, identidad de cuenta/persona, validación S3/hash,
  expediente en DocuCore/TramiCore, adjuntos por tipo, foliación, CUT y asiento
  dentro de la transacción. El cargo sólo se confirma tras COMMIT. Las pruebas
  ejercitan éxito/fallo/rollback con dobles, no una radicación real nueva.
- **CUT:** se conservan secuencia_anual_cut y función canónica. Ninguna consulta
  de esta fase invoca el generador. Las dos pruebas concurrentes de base quedaron
  omitidas; no se creó correlativo_anual ni otra secuencia.
- **Presencial:** catálogo y selección existen, pero el DTO no lleva TUPA UUID o
  código en un campo propio: el frontend prefija el asunto. El servicio no crea
  una relación formal tipo_tramite_id desde esa selección. No se interpreta el
  asunto libre como una clave contractual ni se asigna el primer procedimiento.
  Esto impide declarar completo el enlace formal presencial.
- La columna existente sigd_tra.tramite.codigo_tramite podría participar en una
  solución aprobada; no basta con almacenar texto en asunto. La opción mínima a
  decidir es una entrada opcional explícita y validada por clave natural/UUID,
  persistida transaccionalmente en las relaciones existentes. No se implementó ni
  cambió el DTO unilateralmente; tampoco se hizo backfill de expedientes históricos.
- **Seguimiento:** consulta pública real de EXP-2026-000001 devuelve REGISTRADO,
  sin correo/teléfono ni URL/claves de descarga en metadatos documentales. Se
  conservan las reglas actuales; no equivale a una certificación jurídica de
  publicidad de todos los metadatos. Rutas privadas exigen autenticación.
- **Resoluciones:** se preserva la corrección de Antigravity que sólo acepta una
  asociación institucional comprobable y no reasigna identidades. Su persistencia
  real no se ejecutó; sus 16 unitarias aprobaron en esta regresión.
